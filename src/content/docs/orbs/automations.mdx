自动化让线程在稍后或按重复计划继续工作。跟 Amp 说清楚要做什么、什么时候做即可，不用写 cron，也不用配另一套工作流。

Amp 把计划和提示保存在当前线程。时间到了，Amp 用一条短消息唤醒 agent；agent 用 `get_schedule` 工具读出保存的提示（在线程里可以展开看全文）然后执行。它保留线程的上下文和历史，因此能接着之前的工作，而不是从头开始。orb 线程需要仓库或工具时，Amp 会恢复那个 orb。

计划可以只跑一次，也可以重复。每个线程只能有一个计划；重复计划一直跑到你暂停、删除，到达设定的结束时间，或满足你给的完成条件后由 Amp 清除。

## 示例

```text
每天早上 9:00，找出过去 24 小时里最慢的五个数据库查询。
在这个 orb 里用 ultra 模式逐个排查，然后把清单和结论私信到 Slack。
```

```text
合并这个改动，两天后在 Slack 提醒我把功能开关删掉并向所有人发布。
```

```text
每十分钟检查一次这个 backfill 任务。卡住或开始报错就在 Slack 上叫我。
结束时告诉我，然后停止检查。
```

```text
每小时用 inference-error-triage 技能检查过去一小时的错误并归组。
每个新分组开一个线程去修，并回报到 #bugs 频道。已经处理过的不再报告。
```

## 怎么写好提示

计划提示要说清：

- Amp 该检查或改动什么
- 该回报什么结果，包括"什么都没变"时怎么办
- 结果发到哪里（如果线程本身不够）
- 监控任务什么时候算完成、计划何时该停

时间写在你给 Amp 的请求里，Amp 把它存成计划，其余任务说明存成每次运行的提示。

## 管理自动化

有计划的线程会显示自动化标识，点开能看到标题、计划、下次运行时间和保存的提示，可用开关暂停/恢复，或用垃圾桶删除。也可以直接跟 Amp 说：

```text
把这个计划改成工作日 8:30。
暂停这个自动化，直到我叫你继续。
删除这个计划。
```

一次性计划跑完即完成。运行失败会显示错误；临时的投递错误可能让重复计划保持启用。如果是 Amp 主动暂停了自动化，修好问题后再恢复。

## 在静音线程里悄悄运行

在线程菜单选 **Snooze Until I'm Needed**（或说"静音到周五"）可以让自动化在后台继续跑。计划的运行和事件订阅（比如 GitHub CI 结果）仍会唤醒 agent，但不会把线程拉回侧边栏、也不发通知——除非你要求。想让某次运行把你叫回来，就在提示里写：

```text
每小时检查一次部署队列。如果有部署卡住，取消静音这个线程并告诉我原因。
```

运行中取消静音后，线程回到侧边栏、通知恢复。静音线程等你批准工具或回答问题时会出现在侧边栏并通知你，答完继续静音。你和同事发消息也会结束静音。

每次计划运行后，Amp 会读这次的回复，只有出现"新信息"（有人回复、有东西失败、发现了你让它盯的情况、替你做了事、或向你提问）才结束静音；只报告"没有新问题"则继续隐藏。

## Webhook

插件可以创建公开的 HTTP 端点，用来保存事件并唤醒它所在的 orb。外部服务（比如 GitHub）需要让 orb 开始工作时用它——与 portal 不同，webhook 不暴露 orb 里运行的服务。

Webhook 只在 orb 线程里的[插件](/customization/plugins)中可用（包括自托管 orb）。在插件入口用简短稳定的 key 注册：

```ts
const { url } = await amp.createWebhook({
  key: 'github-events',
  headers: ['x-hub-signature-256'],
  handler: async (event, ctx) => {
    await verifyAndApply(event.id, event.body, event.headers['x-hub-signature-256'], ctx.signal)
  },
})
```

返回的 `url` 接受 `POST`。在 orb 里运行 `amp plugins show-docs` 可以读已安装的 Plugin API。`amp.createWebhook` 在其它加载环境（本地 CLI、`amp plugins list`）会抛错，需要在 orb 线程里重载插件；插件同时要在本地运行时，捕获这个错误即可。

### 投递保证

项目线程里，注册归属"用户 + 项目 + 插件 + key"，所以提交进仓库的插件在项目内另一个线程加载时拿到同一个 URL；最先注册的线程是所有者线程并处理事件。无项目的线程各自独立注册。

同一 key 重复注册在插件重载和 orb 重启后仍是同一 URL。请求先被存储，再返回 HTTP 200，然后唤醒 orb 调用处理函数——200 只代表已入队，不代表处理完成。空闲停止的 orb 会自动恢复；归档所有者线程会让 URL 不可用、暂停投递，恢复线程后才继续。

投递是**至少一次**：把 `event.id` 和处理动作一起存，避免重试重复执行。处理函数有 30 秒；把 `ctx.signal` 传给可取消的网络请求，临时失败就抛错重试。更长的工作放进持久队列或另开线程。

抛错只延后该事件：5 秒后重试、每次翻倍，最多 5 分钟，期间后续事件照常投递，因此不保证顺序。连续一小时被拒的事件会被丢弃并记进 orb 的 Amp 日志。不要用抛错来等无关条件。

### 速率限制

每个端点允许 10 个事件的突发，并以每分钟 10 个补充；超出或积压 100 个时返回 HTTP 429（带 `Retry-After`）。请求体最大 1 MB。重试请带稳定的 `Idempotency-Key`。

### 安全

把 webhook URL 当密码：拿到它的人无需登录 Amp 就能提交事件。不要提交进仓库、不要写进线程消息或普通日志。Amp **不会**替你验证外部服务的签名——把相关 header 列进 `headers`，密钥存到[项目设置](/orbs/secrets)，在处理前自己验签。插件没列出的 header 会被丢弃。请求体和 header 一律当不可信输入，也不要把 webhook 文本当作 agent 指令。

### 触发设置与测试

触发设置里可以暂停（保留 URL、拒绝新事件）或删除（吊销 URL、清空队列）。因线程归档而暂停时，设置里会说明原因并链到那个线程。想让线程长期持有 CI 或 webhook：不要归档所有者线程；去掉让 Amp 干完就归档的指导；CLI 执行模式加 `--no-archive-after-execute`，SDK 设 `noArchiveAfterExecute` / `no_archive_after_execute`。

不把 URL 留在 shell 历史里的测试方式：

```bash
read -rsp 'Webhook URL: ' AMP_WEBHOOK_URL && echo
curl --fail-with-body -X POST \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: test-event-1' \
  --data '{"action":"test"}' \
  "$AMP_WEBHOOK_URL"
unset AMP_WEBHOOK_URL
```
