先给一张截图，再说清楚你希望用户能做什么。Amp 会用你应用里的颜色、字体和文案做出可点击的 HTML 原型，你可以逐个试用、比较，选定方向后再在同一个线程里把它变成代码。

## 从界面和目标开始

附上你想改的页面截图，或者让 Amp 跑起你的应用自己截一张。说明哪里不好用，以及哪些必须保持不变。

```text
这个侧边栏需要显示谁在线，还要能聊天。聊天入口太难找了。
用这张截图探索更好的布局。保留我们的颜色和字体，先别写代码。
```

从零开始时，描述这个屏幕和它的用途即可。

## 比较不同布局

要的是**交互方式**不同的方案，而不只是换个颜色或间距。把你判断设计需要的状态一起写进去，比如展开的菜单。

```text
做三个方向的雏形：人在聊天框上方、头像行加聊天、可展开的紧凑 dock。
把头像菜单打开，让我看到每个人的活跃线程放在哪儿。
```

Amp 会先读你应用的样式与组件，所以原型看起来就像你的应用。它会把当前设计和最多三个方向并排展示，并提供切换。按钮和菜单都能点，因此你能检查行为，而不只是外观。

在 orb 线程里，原型直接出现在对话中，按你的明暗主题渲染在沙箱 iframe 内：没有网络访问，也接触不到你的应用、代码或数据，只能用示例数据且不保存任何内容。CLI 不会在对话里显示原型；在 orb 之外，让 Amp 把原型写成一个独立的 HTML 文件。

## 细化一个方向

选一个方向，说明要保留什么、改什么。同一线程里可以直接用方向的名字指代，不必重述需求。

```text
头像行那个再往前推一步：聊天仍是主视图，在线头像放成一行在它上面，去掉头像上方的导航。
```

Amp 会更新原型，并保留你没有提到的部分。也可以把几个方向拼起来：

```text
用头像行的布局，配 dock 的消息输入框。已打开线程的菜单保持不变。
```

如果要改的是正在运行的真实界面（调内边距、修一个按钮），直接让 Amp 改代码，不要走原型。

## 用 Painter 探索视觉风格

[Painter](/tools) 负责出图。当你只想看"感觉"而不是试交互时（比如给一个还没有界面的新产品做情绪板），点名用 Painter。

```text
用 Painter 给一个安静的深色笔记应用做情绪板，展示三种视觉风格。
```

图像模型可能凭空造控件，也可能漏掉需求，而且不会用你真实的组件。把生成的图当作外观参考，再用原型验证设计是否成立。

三者回答的问题不同：

- **原型**：在对话或浏览器里运行，用来比较方案、验证交互（菜单从哪儿弹出）。
- **Painter**：生成图片，用来探索风格或做素材。
- **Portal**：展示 orb 里真实运行的应用，用你自己的组件和数据验收实现。

## 实现并验收

方向定了，让 Amp 用应用现有的组件去实现。原型是设计参考，不属于你的应用。

```text
用我们现有的组件实现这个侧边栏。头像菜单要显示那个人的活跃线程。
检查键盘导航和窄屏布局，并跑相关测试。
```

既看截图，也看真实运行的应用。在 orb 里让 Amp 给你一个 [portal](/orbs/portals)：

```text
启动 dev server，给我侧边栏的 portal 链接。用足够多的消息展示滚动状态，并把头像菜单打开。
```

用 portal 上的浮动反馈按钮选中元素，把意见发回同一线程。同时自己点一遍：原型无法告诉你真实组件下菜单是否可用、焦点是否正确移动。

## 制作配套素材

Painter 也能为界面出图。独立素材要叠在应用背景上时，要求**透明背景**。

```text
用 Painter 给空聊天状态画一架纸飞机，颜色对齐截图里的蓝。
要透明背景、不带阴影，并在明暗两种背景上各检查一遍。
```

Painter 支持透明 PNG。交付前 Amp 应确认文件确实透明，光看白色或棋盘格背景不算数。完整构图（UI 样机、海报）和自带设计背景的应用图标则应保持不透明。
